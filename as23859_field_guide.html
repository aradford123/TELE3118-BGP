01

The Internet as a network of networks

No single company owns the Internet. It's roughly 75,000 independently-operated networks — universities, ISPs, cloud providers, mobile carriers — each called an Autonomous System (AS), identified by a number. BGP (Border Gateway Protocol) is the language these networks use to tell each other "here's how to reach the addresses I'm responsible for."

Think of it like national postal services. Your local post office doesn't know the specific street in Tokyo — it just knows which international carrier to hand a Japan-bound letter to. That carrier knows the next hop, and so on. No single office holds the whole map; each just knows its next hop and passes along what it has learned. BGP is that same handoff, repeated by routers, roughly 950,000 times a second across the global routing table.

Worked example

AS23859 is one of those ~75,000 networks. It doesn't need to know how to reach every address on Earth — it only needs to know one thing: send everything that isn't mine to AS7575. That single fact is the entire routing table you'll see in section 03.

03

eBGP, iBGP & multi-homing

BGP runs in two modes. eBGP (external) speaks between different ASes — that's the language of the global routing table. iBGP (internal) carries those same routes between routers inside one AS, so every router in a large network agrees on the same view without each one needing its own eBGP session to the outside world.

A network with only one eBGP neighbor is single-homed: if that one link fails, it loses its only path to the rest of the Internet. A multi-homed network has two or more upstreams and can fail over between them.

05

Reading an AS path

Every BGP route carries an AS-PATH attribute: the ordered list of every AS the announcement passed through. Read it right to left — the rightmost number is the origin (who owns the prefix), and each number to its left is one more network the route was relayed through before reaching the observer.

Exercise

The shortest path above is 15692 2914 7575 23859 — 4 hops. The longest is 6 hops. In BGP's default best-path algorithm, shorter AS-PATH generally wins when everything else is equal (see section 08). Why might a shorter observed path not always mean "better" or "faster"? (Hint: AS-PATH length says nothing about physical distance, latency, or link capacity — it only counts network hops.)

06

What's in a RIB

Before a router can choose a "best" route, it needs somewhere to keep every candidate it's heard about. That's the RIB (Routing Information Base) — a router's complete internal table of every route it has learned, from every neighbor, before any selection happens. BGP actually keeps three of these:

  • Adj-RIB-In — the raw routes each individual neighbor has advertised, one table per neighbor, before any filtering. AS23859 has exactly one of these (from AS7575); AARNet has hundreds.
  • Loc-RIB — after import policy and the best-path algorithm (section 08) run over every Adj-RIB-In, this is the single winning route per prefix the router has chosen for itself.
  • Adj-RIB-Out — after export policy, whichever routes from Loc-RIB this router has decided to advertise onward to each neighbor.

Loc-RIB then gets compiled into the FIB (Forwarding Information Base) — the actual, often hardware-accelerated, table a router uses to switch packets. RIB is control-plane bookkeeping ("what do I know about"); FIB is data-plane execution ("what do I do with this packet right now"). In the postal-service analogy from section 01: the RIB is the sorting office's ledger of every route every other office has ever mentioned; the FIB is the label actually slapped on the truck right now.

Where this shows up in the tooling

Route collectors like the RIPE RIS nodes queried throughout this guide don't run real routing decisions — they just record each peer's Adj-RIB-In as-is. Periodically they snapshot that into a full RIB dump (an MRT file, e.g. rib.20260915.0200.bz2), then record only the changes in between as UPDATE files. That's exactly what monocle rib <timestamp> (section 14) reconstructs: it takes the last full dump before your requested time and replays the intervening updates forward to rebuild the table as it stood at that instant.

07

How big is the routing table, really?

As of this run, one full-feed vantage point (RouteViews' AS6447, via Geoff Huston's BGP Routing Table Report) carries 1,127,118 active IPv4 FIB entries from 79,883 distinct ASes (67,221 origin-only — stub networks like AS23859 — 712 transit-only, 11,950 mixed like AS7575). Average AS-PATH length: 3.92 hops (max observed: 14) — consistent with the 3–5 hop paths you read in section 05. IPv6's active table is far smaller: 264,189 entries.

The memory math

That 1,127,118-entry FIB is only part of the picture: this same vantage point actually receives 17,468,864 total RIB entries once you count every peer's copy of every candidate route (a RIB/FIB ratio of 15.5×) — section 06's Adj-RIB-In vs. Loc-RIB distinction, at Internet scale. Forwarding hardware (TCAM) is commonly estimated at roughly 100–150 bytes per entry, which puts the compiled FIB at only about 113–169MB — trivial by today's standards. Naively keeping the entire 17,468,864-entry RIB in that same specialized memory would cost roughly 1.7–2.6GB instead. That gap is exactly why routers don't do that: Loc-RIB (one winner per prefix) is small enough for expensive, fixed-size, ternary-matching hardware; the full RIB lives in ordinary, cheap, expandable RAM on the control plane instead.

A real incident — 512K Day, 2014

On 12 August 2014, the global IPv4 FIB crossed 512,000 entries — and many older Cisco routers had their TCAM hard-partitioned to exactly 512K IPv4 slots (with a separate, mostly-unused 256K reserved for IPv6, which had barely 20,000 routes at the time). Routers that hit the ceiling didn't just refuse new routes: some fell back from hardware to slow software forwarding, others silently dropped or blackholed the overflow. eBay, LastPass, and Microsoft Azure all saw real outages that day. Today's IPv4 FIB, at 1,127,118 entries, is over 2.2× that old ceiling. The fix wasn't more physical memory — it was repartitioning the same TCAM (and, longer-term, buying hardware with bigger tables). "Splitting it up" happens on at least two levels: physically, a chassis router spreads its FIB across multiple forwarding-ASIC line cards, each needing its own synced copy; operationally, edge networks that don't need a full table at all just carry a default route instead, and large ASes scale their internal iBGP mesh (section 03) with route reflectors or confederations rather than a full mesh of sessions.

08

How a route wins: best-path selection

A router that hears about the same prefix from multiple neighbors has to pick exactly one route out of its RIB (section 06) to actually use. It runs a fixed sequence of tie-breakers, roughly in this order:

  1. Highest Local Preference — a locally-set policy value; "prefer this neighbor over that one."
  2. Shortest AS-PATH — fewer hops wins (what you just measured in section 05).
  3. Lowest origin type / MED — finer-grained hints between two connections to the same neighbor AS.
  4. eBGP over iBGP — prefer externally-learned routes over internally-relayed ones.
  5. Lowest IGP metric, then lowest router ID — final tie-breakers so every router converges on the same answer.

None of this is guesswork on a router — it's a strict, deterministic list, evaluated top to bottom until one route wins outright.

Why this exact order? It moves from most intentional to most mechanical:

  • Local Preference is checked first because it's the one signal a human operator set on purpose — a deliberate policy choice like "prefer my cheap peering link over my paid transit." It's iBGP-only (stripped before advertising to another AS), which is exactly why it goes first: it's the network's own voice, before the protocol falls back to any automatic default.
  • AS-PATH length is next because once no one has expressed a preference, BGP needs a cheap, universal fallback. Every route carries an AS-PATH and every router can compare it with zero configuration — the protocol's default proxy for "simpler path," even though hop count says nothing about latency or capacity.
  • MED matters only after that because it's a narrower signal: one neighboring AS hinting which of several links into itself to prefer. It's only ever compared between routes heard from the same neighboring AS — different networks may set MED on completely different scales, so comparing it more broadly would be meaningless.
  • eBGP over iBGP isn't a preference at all — it's a structural safety rule: trust directly-learned external information over routes merely relayed inside your own AS, so two routers in the same AS don't disagree about which path is authoritative.
  • Lowest IGP metric, then lowest router ID are arbitrary tiebreakers whose only job is to guarantee an answer — lowest wins both, by convention, not because a low number means anything about quality. If everything meaningful ties, every router in the AS still has to converge on the exact same single path, and an arbitrary-but-computable value like router ID guarantees that.

Put differently: this is exactly what a fully decentralized system of ~75,000 independent networks needs to always agree on one answer without any central coordinator — intentional policy first, then increasingly mechanical fallbacks, ending in an arbitrary but deterministic tiebreak.

Worked example

AS23859 makes this trivial for itself: with only one neighbor (AS7575), there's nothing to compare — every route out is "the AS7575 route," full stop. Best-path selection only gets interesting once you're multi-homed, like AARNet is — with 6 providers and 425 peers, AARNet's routers run this whole sequence constantly.

Policy is expressed in the routing registry as import and export statements (section 10), and can be influenced remotely by a neighbor via communities (section 09 — next).

09

Communities: tagging routes with extra meaning

A route can carry more than AS-PATH and Local Preference — it can also carry communities: tags, usually written ASN:VALUE, that let one network signal or request a policy action without needing bespoke configuration for every neighbor pair. Communities are opt-in and travel with the route until something strips them.

CommunityMeaning
NO_EXPORT (65535:65281)Don't advertise this route beyond the local AS or confederation
NO_ADVERTISE (65535:65282)Don't advertise this route to any BGP neighbor at all
BLACKHOLE (65535:666)Please drop traffic to this prefix — a coordinated DDoS-mitigation signal (RFC 7999)

Those three are IANA-registered and universally understood. Everything else is operator-defined: each network invents, and sometimes documents, its own numbers for things like geographic tagging, customer-type markers, or "please prepend N times before advertising this onward."

Real example, captured live

Captured live from the same RIS Live firehose used elsewhere in this guide: AS32398 announcing 41.204.10.0/24 carrying 1 community: 6461:5997. Unless you have AS32398's own published community guide, those numbers are meaningless — that's the point. Unlike the well-known ones above, operator-defined communities are private vocabulary: agreed bilaterally or documented unilaterally on a network's own website, never centrally registered.

This is also how a customer can remotely influence the Local Preference decision from section 08 without needing its own config on the upstream's router: many transit providers publish community values like ASN:80 / ASN:90 / ASN:100 that a customer can attach to ask for "low / normal / high preference," and the upstream's router maps that community to an actual local-pref value on receipt.

The routing registry (IRR)

The Internet Routing Registry is a public, distributed database where networks declare, in a structured language called RPSL (RFC 2622), which prefixes they originate and which neighbors they accept routes from. Each RIR runs its own IRR (APNIC's is at whois.apnic.net); records are mirrored between registries so tools anywhere can build route filters from them.

Query it with the whois command line tool, just like looking up a domain. Here's AS23859's actual route: objects — the declarations that say "this prefix is legitimately mine":

11

RPKI & route origin validation

The IRR (section 10) is honor-system data — nothing stops a network from typing a route object for a prefix it doesn't own. RPKI (Resource Public Key Infrastructure) fixes that with cryptography: the legitimate holder of a prefix signs a ROA (Route Origin Authorization) stating "only AS X is allowed to originate this prefix." Routers can then check every announcement against the signed ROA set and label it:

StatusMeaning
validA ROA exists and matches this exact prefix + origin AS
invalidA ROA exists, but names a different origin AS or a shorter max-length — a strong hijack signal
unknownNo ROA covers this prefix at all — RPKI simply has no opinion
Worked example — a real gap

3 of AS23859's 4 prefixes are valid. 203.10.48.0/24 comes back no ROA — querying RIPEstat's validator directly confirms why: "validating_roas": []. Until a ROA covers it, RPKI-aware routers have no cryptographic basis to reject an impostor announcing that same prefix from a different AS.

GET stat.ripe.net/data/rpki-validation/data.json?resource=AS23859&prefix=…RIPEstat API
{
  "status": "unknown",
  "validating_roas": []
}

Important nuance: unknown is not itself an attack — most of the Internet's address space still has no ROA. It just means that one prefix currently has zero cryptographic protection.

12

When BGP goes wrong

BGP was designed in an era of mutual trust between a handful of research networks, and that trust model is still largely how it runs today. That produces a recurring family of real incidents:

  • Route hijack — an AS originates a prefix it doesn't own, accidentally or deliberately, pulling traffic toward itself. RPKI's invalid status (section 11) is the direct countermeasure.
  • Route leak — an AS re-announces routes it only learned for internal use, to neighbors who shouldn't see them, turning a stub network into an accidental transit path.
  • MOAS (Multi-Origin AS) — the same prefix announced by more than one origin AS at once. Sometimes legitimate (anycast), often the first visible symptom of a hijack.
  • Stale registry data — IRR/RPKI objects that no one updates as real topology changes, silently drifting away from the truth.
A real incident — Pakistan Telecom vs. YouTube, 2008

In February 2008, Pakistan Telecom (AS17557) was ordered to block YouTube domestically. Its engineers configured a more-specific /24 route for a piece of YouTube's address space, intending to black-hole it only inside Pakistan — but the route leaked to their upstream, PCCW (AS3491), which propagated it globally. Because a /24 is more specific than YouTube's actual announcement, longest-prefix-match made routers worldwide prefer the fake route, making YouTube unreachable for roughly two hours. No malice was required, just a locally-scoped intention that leaked past its boundary — and it's one of the most frequently cited incidents motivating RPKI's later development.

MOAS check — actually run, not just described

We actually ran this check, rather than just describing it: querying RIPEstat's routing-status for all of AS23859's prefixes (131.236.0.0/16, 129.94.0.0/16, 203.10.48.0/24, 149.171.0.0/16) turns up exactly one origin AS each — AS23859 itself. No MOAS today. That's the boring-but-correct outcome; what matters pedagogically is that the check exists and runs on every regeneration, since a MOAS can appear at any time without warning.

ASPA — the leak-protection layer

RPKI's ROAs (section 10) authenticate origin — they say nothing about the AS-PATH shape a leak exploits. A newer, complementary object called an ASPA (Autonomous System Provider Authorization, RFC 9582) fixes that: a customer publishes "my only valid providers are X, Y, Z," letting a receiving router reject a route whose path shape doesn't match. Querying BGPKIT's cached ASPA set: AS7575 (AARNet) is already named as an authorized provider by 5 other customers (AS4608 (Asia Pacific Network Information Centre), AS24014 (Bond University Limited), AS24390 (University of the South Pacific), AS45163 (APNIC Member Services 2), AS139700 (Capricorn Space Pty Ltd)) — but AS23859 itself has published 0 ASPA records naming AS7575 as its own provider. Like RPKI ROAs a few years ago, ASPA adoption is real but still partial, even between networks that already trust each other operationally.

13

Common misconceptions

Now that sections 01–12 have covered the mechanics, here's where people new to BGP most often get tripped up — each one ties back to something you've already seen above.

Myth: "Shortest AS-PATH wins, so it's the fastest route."

Reality: AS-PATH length is only the second tiebreaker (section 08), checked after Local Preference, and even then it just counts hops — nothing about latency, bandwidth, or physical distance. The exercise in section 05 is built around exactly this trap.

Myth: "BGP is basically OSPF or EIGRP, just bigger."

Reality: IGPs optimize for a metric. BGP optimizes for policy — a human-set business decision (Local Preference, section 08) always outranks anything resembling "shortest" or "best."

Myth: "Some router out there has a map of the whole Internet."

Reality: no router anywhere holds one. Each router only knows what its own neighbors told it (Adj-RIB-In, section 06) — the same postal-relay logic from section 01, all the way down.

Myth: "RPKI-valid means the route is safe to trust."

Reality: RPKI/ROV (section 11) only checks who is allowed to originate a prefix. It says nothing about the AS-PATH shape in between — exactly the gap ASPA (section 12) exists to close.

Myth: "Routers double-check legitimacy before preferring a more-specific route."

Reality: longest-prefix-match is unconditional — a smaller, more-specific block always wins over a bigger covering one, from whoever announces it. That single rule is exactly what made the 2008 Pakistan Telecom/YouTube hijack (section 12) propagate globally instead of staying local.

Myth: "BGP reroutes almost instantly, like a phone switching Wi-Fi networks."

Reality: global convergence after a real change can take tens of seconds to minutes. Routers "path-hunt" through less-preferred alternatives before settling, and propagation crosses potentially hundreds of ASes one hop at a time.

Glossary & key takeaways

AS (Autonomous System)
An independently-operated network with its own routing policy, identified by an AS number.
AS-PATH
The ordered list of ASes a route passed through; read right-to-left, with the origin AS as the rightmost entry.
RIB / FIB
RIB: every route a router has learned, before selection (Adj-RIB-In/Loc-RIB/Adj-RIB-Out). FIB: the compiled table actually used to forward packets.
TCAM
Ternary Content-Addressable Memory — specialized, expensive, fixed-size hardware memory routers use to hold the FIB for line-rate forwarding.
eBGP / iBGP
BGP between different ASes, versus BGP between routers inside the same AS.
Single- / multi-homed
One upstream versus two-or-more; determines failover resilience.
Community
An ASN:VALUE tag on a route used to signal or request a policy action; some are IANA-standard (NO_EXPORT), most are operator-defined.
IRR / RPSL
The public registry (and its declaration language) where networks state ownership and policy.
ROA
A signed statement: "only this AS may originate this prefix."
RPKI / ROV
The cryptographic system built on ROAs, and the act of checking routes against them.
ASPA
Autonomous System Provider Authorization — a signed list of an AS's valid providers, used to detect route leaks (a path-shape problem ROAs don't cover).
MOAS
The same prefix announced by more than one origin AS — sometimes legitimate, often a hijack signal.
Stub network
An AS that only originates its own routes and never carries anyone else's traffic — like AS23859.
Customer cone
Every AS reachable downstream of a given AS through customer relationships — a rough proxy for size/influence.

Four takeaways to remember AS23859 by:

  1. A stub network's routing table can be almost entirely explained by one relationship — here, "send it all to AS7575."
  2. Trust in BGP is layered: IRR declares intent (unverified), RPKI cryptographically proves origin (verified, but not universal).
  3. Real registries accumulate cruft. A stale policy object referencing a dead AS is not a crisis — but at Internet scale, this exact kind of drift is the raw material real incidents are made of.
  4. Scale bites in unglamorous ways: a full IPv4 table is only tens of megabytes of actual data, but a hard-coded hardware partition size (not "not enough RAM") is what took down eBay, LastPass, and Azure for a few hours in 2014.
